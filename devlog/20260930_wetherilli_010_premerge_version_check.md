# wetherilli 010 — 병합 전에 판이 부딪히는지 본다

2026-09-30 · `feature/ui-polish`

## 1. 왜

연구자: "병합 전에 판이 다른지 그런 것들 확인하는 절차를 두도록 해줘. 혹시 충돌이 날 수도 있잖아." 09-30 부터 사람마다
자기 계정에서 `feature/` 브랜치로 일하고 PR 로 합친다. 두 사람이 같은 날 저마다 "0.16.0" 을 적으면 — `version.py` 한 줄은
똑같은 고침이라 git 이 충돌로 보지 않고, CHANGELOG 는 0.16.0 절이 둘이 되거나 한쪽이 다른 쪽 내용을 덮는다. 먼저 병합된
판이 있는데 뒤에 온 PR 이 main 위로 올리지 않고 들어가면, 태그 `v0.16.0` 이 이미 있어 릴리스·이미지가 엉킨다.
지금까지는 CI 가 시험과 굽기만 보았다.

## 2. 무엇을 했나

- `deploy/check_version.py`(표준 라이브러리만) — 브랜치(또는 작업 트리)를 main 과 견준다
  1. `version.py` 판 = CHANGELOG 맨 위 판
  2. CHANGELOG 에 같은 판 절이 둘 없다
  3. main 의 맨 위 판 절이 브랜치에 있다 — 없으면 main 에 다른 판이 먼저 들어간 것이다
  4. 판이 main 보다 낮지 않다. **같으면 그 절의 내용도 main 과 똑같아야** 한다(판을 올리지 않는 PR). 다르면 다른 PR 이
     같은 판 번호를 먼저 썼다
  5. 올린 판의 태그 `v<판>` 이 로컬·원격 어디에도 없다
- CI 에 **"판 확인"** 작업 — PR 일 때만, merge 커밋이 아니라 PR 머리를 main 과 견준다
- `deploy/host/premerge.sh <PR>` — 병합 직전에 돌린다. GitHub 의 병합 가능 여부(글자 충돌), main 보다 뒤처졌는지,
  판 확인, CI 결과. 모두 통과하면 병합 명령을 적어 줄 뿐 **병합하지는 않는다** — 병합은 사람이 정한다
- CLAUDE.md "커밋과 PR" 에 절차를 적었다

판을 낮추거나(0.15.2), main 과 같은 판을 다른 내용으로 적은(0.15.3) 작업 트리로 돌려 FAIL 이 나는 것을 보았다.

## 3. 버린 것

- **뒤처진 브랜치도 판만 맞으면 통과** — main 에 새 커밋이 있으면 시험을 그 위에서 다시 돌려야 한다. premerge 는
  뒤처지면 멈춘다(CI 의 판 확인은 판만 본다 — PR 이 열린 뒤 main 이 움직이면 CI 가 다시 돌지 않기 때문에 사람의 확인이 따로 있다)
- **GitHub 의 "브랜치 보호 — 최신이어야 병합"** — 저장소 설정을 바꾸는 일이라 연구자가 정할 것이다. 필요하면 그때 켠다
