# 013 — 노릭절 채집지가 지도에서 통째로 빠지던 것을 고친다

2026-09-29 · `work/20260929-koprifossillab`

## 1. 어떻게 찾았나

012 를 시험하다가 Coelophysis 의 트라이아스기 칩을 누르니 205 Ma 지도에 채집지가 **1 곳**이었다.
절 단위 분포(010)는 그 무렵 산출이 24 건이라 했다. PBDB 에 직접 물어 보니 24 건 가운데 22 건이
`Norian (227.3–205.7)` — 범위 **21.6 Myr** 였다.

## 2. 무엇이 틀렸나

001 은 채집지 연대 범위의 상한을 20 Myr 로 두고 "가장 긴 절(노리절 등)이 들어오는 값" 이라 적었다.
노릭절은 옛 판에서 약 18.5 Myr 였지만 **ICS 2024(와 PBDB)는 227.3–205.7, 21.6 Myr** 다. 절 하나로만
매겨진 노릭절 채집지가 **모두** 빠져 있었다. 전체 자료에서 1,567 곳이다.

20 을 넘는 다른 것도 셌다(전체 채집지 278,398):

| 연대 | 범위 | 채집지 |
|---|---|---|
| Norian | 21.6 | 1,567 |
| Aptian–Albian | 20.9 | 330 |
| Miocene–Pliocene | 20.46 | 267 |
| Neogene | 20.46 | 179 |
| Llandovery–Ludlow | 20.4 | 61 |
| Neocomian–Barremian | 21.7 | 32 |

## 3. 상한 = 가장 긴 절의 길이

숫자를 다시 적지 않고 **층서표(`timescale.py`)에서 가장 긴 절의 길이**로 정한다 — 지금은 노릭절 21.6.
원칙은 "절 하나로 매겨진 채집지는 하나도 빠지지 않는다" 이고, 층서표를 새 판으로 올리면 상한도 따라간다.
22 처럼 둥근 수로 올리면 원칙이 흐려지고, 절 둘에 걸친 21.7(Neocomian–Barremian)이 들어온다.

227.3 − 205.7 은 부동소수로 21.600000000000023 이라, 비교에 1e-6 의 허용을 둔다(시험이 지킨다).

**뷰어도 같은 값을 쓴다.** 전에는 map.js 에 `MAX_SPAN_MA = 20` 을 따로 적어 두었다 — 파이프라인만 고치면
분류군 찾기가 여전히 20 으로 걸렀을 것이다. 이제 `index.json` 의 `rules`(`window_ma`·`max_span_ma`)로 받는다.

결과: 205 Ma 지도의 채집지 2,357 → 3,799 곳, Coelophysis 는 1 → 17 곳.

## 4. 다시 가공해도 브라우저가 옛 파일을 보였다

고친 뒤에도 브라우저가 205 Ma 에 2,357 곳을 보였다. 시점 파일은 하루 캐시하고(`views.FRAME_MAX_AGE`) 다시
가공해도 파일 이름이 같기 때문이다. 운영에서 PBDB 를 새로 받아 가공해도 하루 동안 옛 자료가 보였을 것이다.
시점 파일의 주소에 **가공 시각**(`index.json` 의 `built_at`)을 붙여, 가공할 때마다 새 주소가 되게 했다.
`index.json` 자체는 5 분만 캐시하므로 새 가공이 늦어도 5 분 안에 보인다.
